# МЭШ — Помощник учителя

Chrome MV3 расширение для `school.mos.ru` (Московская электронная школа — МЭШ):
подсветка проблемных учеников, контроль/проверка итоговых оценок, анализ
пропусков, экспорт в Excel/CSV на уровне одного класса, всех классов по
предмету и — для администрации школы — по всей параллели/школе сразу.

Рабочая ветка: `claude/repository-review-cmv02q`. Релизные снимки истории
лежат в ветках `Релиз`/`Релиз-2` (обновляются fast-forward'ом от рабочей
ветки, когда просят «скопировать на релиз»). Бизнес-план публикации, цены,
лицензирование и юр.часть — отдельно в `PUBLICATION_PLAN.md` (ещё не
реализовано в коде, только решения на словах) — не путать с этим файлом.

## Как это физически работает

Расширение не трогает сервер МЭШ и ничего никуда не отправляет — это
полностью клиентский инструмент. Данные (оценки, посещаемость, расписание)
добывает **пассивным перехватом** уже идущих сетевых запросов самой
страницы, а не прямыми вызовами API:

1. `marks-api-bridge.js` (content script, `document_start`, isolated world)
   инжектит `marks-api-hook.js` в **MAIN world** страницы через
   `<script src="chrome.runtime.getURL(...)">` (см. `web_accessible_resources`
   в manifest.json).
2. `marks-api-hook.js` в MAIN world патчит `window.fetch`/`XMLHttpRequest`,
   фильтрует запросы по списку путей (`EXTRA_PARTS` — marks, groups,
   student_profiles, attendances, schedule_items, homeworks,
   homework_absences, emias_medical_recommendations, final_marks,
   attestation_periods_schedules), клонирует и парсит JSON-ответы, шлёт их
   через `window.postMessage(..., window.location.origin)` (НЕ `"*"`).
3. `marks-api-bridge.js` ловит эти сообщения (`event.source === window &&
   data.source === SOURCE` — двойная проверка, без неё любой скрипт на
   странице мог бы подделать данные), копит их в
   `window.__MESH_HELPER_API__` (накопительно, не затирая друг друга) и
   шлёт DOM-события (`mesh-helper-marks-updated`,
   `mesh-helper-api-updated`) остальным content scripts.

Остальные модули (`hybrid-counter.js`, `class-auto-loader.js`,
`admin-collector.js` и т.д.) читают `window.__MESH_HELPER_API__` напрямую —
никто, кроме bridge/hook, сеть не трогает.

**Важное следствие:** если нужны данные из НОВОГО эндпоинта — сначала
добавь путь в `EXTRA_PARTS` (marks-api-hook.js) и маппинг в
`apiKindFromUrl()` (marks-api-bridge.js), только потом читай
`window.__MESH_HELPER_API__.<kind>` из остальных модулей.

## Жёсткое правило: никогда не гадать формат API вживую непроверенных данных

Это самое дорогое правило в проекте, выстраданное на реальном инциденте.
Была фича «Н по болезни»: первая реализация угадала поле
(`absence_reason_id`), оказалась неверной (нашлись контрпримеры), пришлось
полностью ревертить и переделывать через живое исследование DevTools
(Network/data-test-component атрибуты) — нашли реальный источник
(`/emias_medical_recommendations`). После этого правило: **если не видел
реальный ответ API/реальную DOM-структуру — не пиши логику на основе
предположения о её форме**, если можно вместо этого:
- переиспользовать уже ПРОВЕРЕННЫЙ способ получения данных (DOM-паттерны
  из уже работающих модулей — см. ниже «проверка итогов через DOM»), или
- явно попросить пользователя проверить вживую (DevTools → Network →
  посмотреть реальный ответ, прислать скриншот/JSON) и подождать, прежде
  чем писать логику.

Пример: `/final_marks` и `/attestation_periods_schedules` перехватываются
(см. `EXTRA_PARTS`) и складываются в `window.__MESH_HELPER_API__.finalMarks`
/`.periods`, но их JSON-форма ни разу не проверялась вживую — поэтому
«Проверка итогов» вместо них читает итоговые/периодные оценки **из
отрисованной DOM-таблицы** через уже доказанно-рабочий паттерн
`data-test-component`-атрибутов (см. ниже), а не гадает JSON.

## «Проверка итогов через DOM» — проверенный паттерн атрибутов

`school.mos.ru` (MUI/React) кодирует сущности прямо в атрибуте
`data-test-component`. Подтверждённые вживую селекторы (используются в
`hybrid-counter.js`/`final-control.js`/`admin-collector.js`):

- `[data-test-component^="markCell-"]` в строке ученика — его атрибут имеет
  вид `markCell-<studentId>_<lessonId>_...`; `studentId` из него совпадает
  с `student_profile_id` из API (сверено вживую в `hybrid-counter.js`) —
  это способ связать DOM-строку с реальным ID ученика без похода в API.
- `[data-test-component*="finalResult"]` — ячейка итога за период.
- `[data-test-component*="yearResult"]` — ячейка итога за год.
- `[data-test-component*="average"]` — ячейка среднего балла.

`admin-collector.js` переиспользует именно эти селекторы
(`captureFinalGradesForJournal()`) для сбора итогов в фоновой вкладке —
это НЕ ново изобретённый способ, а перенос уже проверенного паттерна в
контекст батч-сбора. Если он когда-нибудь перестанет находить данные
(например, МЭШ сменит вёрстку) — чинить тем же методом: смотреть вживую,
не гадать.

## Хранилище: три независимых батч-системы в режиме администратора

В админ-режиме **три параллельных, полностью независимых** сбора — у
каждого свой storage key, свой `resumeXIfRunning()`, своя фоновая вкладка.
Общая механика навигации по вкладкам — в `background.js`
(`startBackgroundBatch`/`advanceBackgroundBatch`/`stopBackgroundBatch`,
параметризованы `storageKey`, поэтому несколько независимых батчей могут
использовать одну и ту же инфраструктуру не мешая друг другу).

| Сбор | Storage key (running) | Storage key (results) | Что ждёт | Зачем лёгкий |
|---|---|---|---|---|
| Полный (Excel/СВОД/Аналитика/ДЗ) | `meshHelperAdminBatch` | `meshHelperAdminLastResults` | marks, schedule, homeworkAbsences, studentProfiles, attendances, medicalRecommendations, финалы из DOM | — (нужно всё) |
| Проверка итогов | `meshHelperAdminFinalsBatch` | `meshHelperAdminFinalsLastResults` | marks, studentProfiles, DOM-итоги | не ждёт расписание/посещаемость/ДЗ/мед.данные |
| Отсутствует ДЗ | `meshHelperAdminHomeworkBatch` | `meshHelperAdminHomeworkLastResults` | только schedule + homeworkAbsences | самый лёгкий — не ждёт даже marks/учеников |

Каждый батч-объект в storage: `{status: running|done|stopped|error, mode:
"background", queue: [...], currentIndex, results: {}, errorMessage?}`.
При ошибке сохранения (`chrome.storage.local` квота — лимит 5MB без
`unlimitedStorage`, которое ЕСТЬ в manifest.json) статус переходит в
`"error"` вместо тихой потери данных (см. ниже «storage-квота»).

Если нужен **четвёртый** независимый сбор — копировать этот паттерн
1:1: новый `ADMIN_X_STORAGE_KEY`/`ADMIN_X_LAST_RESULTS_KEY` в
admin-collector.js, свой `resumeAdminXBatchIfRunning()` с минимально
нужным списком `waitForAdminApiKind(...)`, свой `collectXForSelectedClasses()`
вызывающий `startAdminBatchInBackground(journals, KEY, "метка")`, вызов
`resumeAdminXBatchIfRunning()` в конце файла рядом с остальными.

## UI: выезжающие drawer'ы, а не инлайн-аккордеоны

Три кнопки-входа режима администратора («Режим администратора», «Проверка
итогов», «Отсутствует ДЗ») сидят в ОДНОЙ общей плашке `#mh-admin-group` в
основной панели, но открывают **три независимых** drawer'а — отдельный
файл на каждый, полностью самодостаточный паттерн, скопированный с
`notes-panel.js` («Заметки к классу» — первый drawer в проекте):

- `admin-drawer.js` → `#mesh-helper-admin-drawer`
- `finals-check-drawer.js` → `#mesh-helper-finals-drawer` (там же —
  настройка «Критерии округления итоговой», та же что в основной
  панели, т.к. СВОД использует именно её для «итог не совпадает с
  расчётным»)
- `homework-check-drawer.js` → `#mesh-helper-homework-drawer`

Общий визуал — `admin-drawer.css` (`.mhad-drawer`/`.mhad-open`/
`.mhad-header`/`.mhad-title`/`.mhad-close`), контент внутри переиспользует
уже существующие глобальные классы из `class-panel.css` (пороги, пикер,
кнопки, прогресс, статус) — НЕ дублирует стили под новый drawer.

Паттерн drawer-файла (копировать при добавлении нового):
- IIFE с `window.__meshHelperXDrawerInstalled` guard.
- `ensureDrawer()` — создаёт DOM один раз, вешает обработчики.
- `positionDrawer()` — слева от основной панели
  (`panel.getBoundingClientRect()`), либо фиксированный fallback если
  панели ещё нет.
- `ensureToggleButton()` — ищет кнопку+секцию ВНУТРИ `#mesh-helper-panel`,
  переключает видимость секции по `isAdminJournalsListPage()`, вызывается
  по таймеру `setInterval(..., 1000)` (панель рисуется другим content
  script'ом асинхронно — race condition, поэтому retry, а не once).
- `chrome.storage.onChanged` слушатель СВОЕГО storage key — drawer сам
  следит за прогрессом, не полагаясь на `panel-shell.js`.

**Не объединять независимые сборы в один drawer** — это уже явно
отклонённый пользователем вариант (один раз предложил «слить всё в один
большой drawer с под-секциями», получил чёткое «НЕТ» — разные кнопки,
разные панели, ничего общего визуально/логически между независимыми
сборами, даже если соблазнительно сэкономить на разметке).

## Экспорт в Excel: `class-workbook.js`

Рукописный генератор `.xlsx` (OOXML/SpreadsheetML) без зависимостей —
строит zip вручную (свой `crc32`/`zip()`), XML руками. Публичный API:
`row()`, `worksheet()`, `formula()`, `downloadWorkbook()`,
`buildWorkbookBlob()`, `paletteStyleId()`.

- Стили — `STYLE` map (`Default/Header/BadFinal/BadAbsence/Highlight`) +
  **динамическая палитра** для листа «Аналитика» в админ-выгрузке: цвет
  каждого предмета считается по формуле HSL (`paletteColorHex(index,
  total)`), а не берётся из фиксированного списка — сколько бы предметов
  ни было, каждый получает уникальный, не повторяющийся цвет (раньше был
  фиксированный список из 6 — ломался на 7+ предметах, предметов может
  быть больше, подсвечивать нужно каждый). `stylesXml(paletteCount)`
  генерирует N пар заливок/стилей (data+header) поверх фиксированных 5;
  `resolveStyleIndex()` разбирает `Pal{index}`/`Pal{index}Header`.
- Числа с десятичными **в CSV** (не в xlsx) нужно писать с запятой, не
  точкой — иначе Excel в RU-локали может принять «3.02» за дату («03.фев»,
  `апр.71` и т.п.). В xlsx эта проблема не возникает (ячейки типизированы
  явно), трогать `.replace(".", ",")` нужно только в csv-строках.
- Объединение ячеек (`mergeCells`) — порядок элементов в sheetXml важен:
  `<autoFilter>` → `<mergeCells>` → `<conditionalFormatting>` →
  `<dataValidations>` (OOXML-спека чувствительна к порядку).
- `freezeRows`/`filterStartRow` настраиваются по листу — используется,
  когда сверху таблицы есть строка-баннер/сводка (например, 2-строчная
  шапка «общий средний балл» над листом предмета, или СВОД с параметрами
  в первой строке и реальными заголовками во второй).

## CSV: защита от формульной инъекции (OWASP CSV Injection)

`csvValue()` (дублируется в `hybrid-counter.js`/`admin-collector.js`/
`class-auto-loader.js` — да, сознательно не вынесено в общий модуль,
проект НЕ использует сборщик, каждый content script самодостаточен) ДОЛЖНА
экранировать значения, начинающиеся с `=`, `+`, `-`, `@`, таба — иначе
Excel при открытии файла интерпретирует их как формулу. Текущая реализация
добавляет ведущий апостроф:
```js
function csvValue(value) {
  let str = String(value ?? "");
  if (/^[=+\-@\t\r]/.test(str)) str = "'" + str;
  return `"${str.replace(/"/g, '""')}"`;
}
```
Если добавляешь НОВУЮ csv-сборку — копировать эту функцию, не писать
`"${value}"` напрямую.

## Безопасность: что уже проверено и закрыто

Полный аудит проводился в сессии (см. git-историю коммитов с «безопасность»
в сообщении). Текущее состояние:
- Нет эксфильтрации данных — расширение не делает сетевых запросов ни на
  один сторонний домен, все экспорты — локальные Blob-файлы.
- Минимальные `permissions`: `storage`, `unlimitedStorage`. Никаких
  `tabs`/`webRequest`/`cookies`/`<all_urls>`.
- `postMessage` — targetOrigin всегда конкретный origin, не `"*"`;
  приёмник проверяет и `event.source === window`, и `data.source`.
- Везде, где в `innerHTML` попадают данные из API/DOM (имена учеников и
  т.п.) — проходят через `esc()`/`escapeHtml()` (экранирование &, <, >,
  ", '). Там, где возможно — `createElement`+`textContent` вместо
  `innerHTML` вообще (пикеры классов).
- CSV-инъекция формул закрыта (см. выше).
- Explicit CSP в manifest.json (`script-src 'self'; object-src 'self'`) —
  совпадает со строгим default MV3, но зафиксирован явно.
- Разделение `chrome.storage.sync` (только некритичные настройки-пороги,
  синхронизируются через аккаунт Google — туда НИКОГДА не пишутся данные
  учеников) и `chrome.storage.local` (все собранные данные, включая
  медицинские отметки — только локально, не синхронизируется).
- Удалено ~2600 строк мёртвого legacy-кода (12 файлов, не подключённых в
  manifest.json) — если видишь файл в `src/`, которого нет в
  `manifest.json` `content_scripts`/`background`/`web_accessible_resources`
  и на который никто не ссылается по имени — это, скорее всего, случайно
  оставленный черновик, проверь перед использованием.

**Если добавляешь новую CSV/xlsx-выгрузку или новое поле, попадающее в
`innerHTML`** — применяй оба правила (csvValue-экранирование формул,
HTML-экранирование) по умолчанию, не только когда «заметил проблему».

## storage-квота: `chrome.storage.local` ограничен 5MB

При сборе МНОГИХ журналов (марки+посещаемость+расписание+мед.данные по
каждому ученику каждого предмета) легко превысить лимит без
`unlimitedStorage` — эта проблема реально случилась («собрал всё, но
скачать нечего» — финальная запись падала по квоте молча). Исправлено
двумя вещами:
1. `unlimitedStorage` в manifest.json permissions (главное исправление).
2. `setStorage()` теперь возвращает `true`/`false` об успехе записи;
   если финальная запись результатов не удалась — батч переходит в
   статус `"error"` с понятным `errorMessage`, видимым в UI, вместо
   тихой потери данных.

Если добавляешь новый батч — обязательно проверяй результат `setStorage()`
при сохранении финальных результатов, не полагайся молча на успех.

## Дизайн-система панели

Редизайн панели (8 пунктов, см. git-историю «Дизайн, пункт N») + два
доп. усиления (иконки/анимация) привели к следующим правилам:

- **Токены** — `panel-tokens.css`, `:root`-scoped custom properties
  (`--mh-*`). Единственный источник цвета/отступов — хардкод хексов в
  остальных CSS запрещён де-факто (весь существующий код уже переведён).
  Шкала отступов — `--mh-space-1..5` (4/6/8/10/12px) для **margin/gap
  между элементами** (не для padding внутри компонента — он подобран
  вместе с размерами конкретной кнопки/поля и не унифицирован намеренно).
- **Иерархия шрифтов**: 800 — только главный заголовок панели и кнопка
  «Сохранить»; 700 — заголовки секций/CTA-кнопки; 600 — второстепенные
  кнопки/подписи порогов; 500 — пункты списков/статус-тексты. (На
  системных шрифтах веса 650–900 визуально неотличимы от жирного —
  раньше всё «кричало» одинаково.)
- **Иерархия кнопок**: заливка-градиент (`.mh-class-export-btn`) — только
  для ГЛАВНОГО действия секции (запустить сбор). Второстепенные/
  последующие действия (скачать результат, сохранить критерии) —
  `.mh-btn-secondary` (плоская, обводка акцентом, без градиента/тени).
- **Иконки** — inline SVG (`.mh-icon`, 14×14, `stroke="currentColor"`),
  НЕ эмодзи (эмодзи по-разному рисуются на разных ОС, выбиваются из
  общего стиля — раньше были, заменены).
- **Единый акцент вместо «радуги»** — карточки-секции все на одном
  нейтральном фоне (`var(--mh-surface-muted)`), секции различает иконка
  в заголовке, не цвет фона.
- **Свёрнутая «таблетка»** (мини-режим панели) — красная (не синяя!).
  Осознанный выбор ради контраста: весь остальной UI school.mos.ru и так
  сине-фиолетовый, синяя таблетка в нём визуально теряется.
- **Плавное раскрытие** аккордеон-секций — через `setMenuExpanded()`
  (max-height, измеряется `scrollHeight` в момент клика, после открытия
  снимается ограничение `max-height: none`, чтобы контент мог дальше расти
  без обрезки). При первой отрисовке (из localStorage) анимация
  ПРОПУСКАЕТСЯ — иначе дёргается при каждом открытии страницы.
  ⚠️ Если анимируешь несколько CSS-свойств одним `transitionend`-
  слушателем — НЕ используй `{once: true}}`, он может сработать на первом
  же сработавшем свойстве (не обязательно на том, что реально отслеживаешь)
  и снять слушатель раньше времени; снимай вручную и только по нужному
  `e.propertyName`.

## Проверка перед коммитом (обязательно для xlsx/CSV-логики)

В проекте нет сборщика и нет автотестов в привычном смысле — но для
КАЖДОГО изменения, затрагивающего генерацию `.xlsx`/`.csv`, принятая
практика: Node.js `vm`-песочница, загружающая реальный файл модуля,
стабящая `chrome`/`document`/`Blob`/`URL`/`TextEncoder`, реально строящая
файл и проверяющая результат через `zipfile`/`xml.dom.minidom` (Python)
или прямым regex-разбором XML. Для проверки DOM-парсинга (например,
`captureFinalGradesForJournal()`) — патчить копию файла, временно
экспортируя внутренние функции на `window.__TEST_EXPOSE__` (сам файл в
репозитории не трогать, патчить только копию в scratchpad).

Частые грабли при такой песочнице:
- `FakeBlob`/проверка `instanceof Uint8Array` не работает между realms
  vm-контекста и хоста — использовать `ArrayBuffer.isView(x)` вместо
  `instanceof`.
- `URLSearchParams`, `window.addEventListener`/`removeEventListener` нужно
  явно стабить, если код их вызывает (`currentAdminJournalIdFromQuery`,
  `waitForAdminMarks` и т.п.).

`node --check src/<file>.js` — минимум перед каждым коммитом, трогающим JS.

## Атрибуция коммитов

Каждый коммит должен заканчиваться (см. системные инструкции текущей
сессии за актуальным форматом — он может включать session-specific ссылку,
которая меняется от сессии к сессии):
```
Co-Authored-By: Claude <модель> <noreply@anthropic.com>
Claude-Session: <ссылка сессии>
```
Никогда не указывать модель/версию Claude в коде, PR-описаниях или
коммит-сообщениях ПОМИМО этой финальной trailer-строки.

  таковое, не скрытое допущение.
