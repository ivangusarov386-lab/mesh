# МЭШ — Помощник учителя: план подготовки к публикации

Рабочие заметки по итогам обсуждения (октябрь 2026). Фиксирует принятые решения
по публикации, FREE/PRO, лицензированию и юридической части — чтобы продолжить
с этого места в следующем разговоре, не пересказывая всё заново.

Это не финальный документ, а рабочий черновик решений. Тексты оферты/политики
ПДн перед реальным приёмом денег должен проверить юрист.

## 1. Какую версию публиковать

- Публикуем текущую рабочую ветку (`claude/repository-review-cmv02q` на момент
  записи), не `master` и не `stable-export-v2` — только в ней «Мой класс»
  реально проверен на живых данных.
- Перед релизом:
  1. Поднять версию в `manifest.json` (например, `1.4.0`).
  2. Удалить неиспользуемые файлы из `src/`: `class-average-override.js`,
     `class-data.js`, `class-export.js`, `class-subject-sheet.js`,
     `class-summary-sheet.js`, `class-workbook-export.js`, `content.js`,
     `highlight-default-on.js`, `highlight-guard.js`, `marks-api-test.js`,
     `period-counts.js`, `selection-export.js`.
     (`class-workbook.js` и `class-panel.css` — оставить, используются.)
  3. Смержить рабочую ветку в `master` как новую релизную точку.
  4. Финальный regression-тест на реальном классе: подсветка, контроль/проверка
     итогов, CSV текущего журнала, «Мой класс» (оценки, Н%, часы, итоги).

## 2. FREE / PRO

| Функция | FREE | PRO |
|---|---|---|
| Подсчёт оценок (DOM+API) | ✅ | ✅ |
| Минимум оценок + подсветка недобора | ✅ | ✅ |
| Контроль отсутствующих итогов | ❌ | ✅ |
| Проверка корректности итогов | ❌ | ✅ |
| Анализ пропусков (текущий журнал) | ❌ | ✅ |
| CSV текущего журнала | ✅ (проблемные) | ✅ (весь класс) |
| «Мой класс» — Excel по всем предметам, Н%, часы | ❌ | ✅ |
| Настраиваемый порог «проблемный средний балл» | — | ✅ |
| Настройка порога «минимум оценок» (изменить число) | ❌ (фиксировано на **5**, дефолт) | ✅ (любое число) |

**Решение по порогу минимума оценок:** в FREE остаётся тот же проверенный
дефолт **5** (не урезанное число вроде 3 — это портило бы саму точность
подсветки, а не просто гибкость). PRO-фича — именно возможность **поменять**
число под конкретный предмет, а не доступ к самой подсветке.

**Триал:** 7–14 дней полного PRO при первой установке, без привязки карты.

**Технически:** нужен единый слой `canUse('finalControl')` и т.п. — не размазывать
проверки тарифа по модулям. Ещё не реализован, реализуется перед включением
платёжной части.

## 2.1 Цены

| Срок | Цена | В пересчёте на месяц | Скидка |
|---|---|---|---|
| 1 месяц | 249 ₽ | 249 ₽ | — (база) |
| 3 месяца | 599 ₽ | ≈200 ₽ | ~20% |

**Решение: тариф на 6 месяцев убран, остаются только 1 и 3 месяца.**
Причина — двойная, и оба аргумента независимо указали на один вывод:

1. **Календарная логика (ключевой аргумент владельца):** учебный год — это
   9 месяцев. 3-месячный тариф делится на него ровно 3 раза — платёж в
   сентябре, декабре, марте полностью закрывает год без остатка. 6-месячный
   тариф в этот цикл не вписывался: либо прихватывал кусок лета (простой,
   когда журнал не нужен — оценки и посещаемость летом не ведутся), либо
   обрывался в неудобной точке внутри учебного года.
2. **Финансовый риск (см. также правки ниже):** без 6-месячного тарифа
   максимальная предоплата с одного пользователя — 599₽, а не 999₽, что
   меньше «замораживает» будущую выручку и меньше давит на cash flow при
   росте базы.

Если после запуска 3-месячный тариф (теперь — самый длинный commitment)
будет непопулярен из-за скидки всего ~20%, разумно усилить скидку (например,
549₽), а не возвращать промежуточный 6-месячный тариф.

Ориентир цены — психологически знакомая цена похожих подписок (владелец
называл ~250₽/мес за DNS-сервис) и то, что МЭШ — только Москва, аудитория с
доходом выше среднероссийского.

**Ранние покупатели фиксируют сегодняшнюю цену себе навсегда** — цена для
новых когорт может расти со временем (принцип из самого раннего обсуждения
проекта, подтверждён).

**Второе устройство — в план развития, не в запуск** (см. раздел 8). Сейчас
лимит строго 1 устройство на ID (раздел 5).

## 3. Налоги и эквайринг

- Статус: **ИП, АУСН** (автоматизированная упрощёнка).
- Перед подключением эквайринга проверить: Сбербанк — банк-партнёр АУСН (почти
  наверняка да, но свериться с банком/личным кабинетом налогоплательщика).
- Касса — брать «как услугу» у эквайринга/банка, отдельную физическую/облачную
  кассу покупать не нужно.
- На АУСН фиксированные страховые взносы ИП **не платятся** — это компенсируется
  более высокой ставкой налога (обычно 8% «доходы» для такого бизнеса, без
  существенных расходов «доходы минус расходы» 20% невыгодны).
- Проверить, что ОКВЭД ИП соответствует продаже ПО/цифровых услуг — иначе банк
  может отказать в подключении эквайринга.
- Рекуррентные платежи (автосписание каждый месяц) — поддерживаются эквайрингом
  Сбербанка для ИП напрямую.

## 4. Юридические документы

**Важное обновление после перехода на ID-схему (раздел 5):** раз теперь
система не собирает email/телефон/ФИО вообще, а только случайный
несвязанный с личностью ID — это, вероятно, существенно снижает (возможно,
вообще снимает) обязанности именно по лицензированию как по обработке
персональных данных: 152-ФЗ применяется к данным, которые идентифицируют
конкретного человека, а случайный ID сам по себе никого не идентифицирует.
**Это не стопроцентная гарантия** — юрист должен подтвердить именно этот
нюанс (может ли ID считаться «косвенно идентифицирующим» из-за связи с
платежом у эквайринга) — но направление явно в вашу пользу. Сам эквайринг
при этом всё равно будет собирать данные покупателя для чека — но это уже
обязанность эквайринга как отдельного оператора, не ваша.

Обязательные:
1. **Политика обработки персональных данных** (152-ФЗ) — нужна, если хоть
   где-то (служба поддержки, email для связи и т.п.) всё же появляются
   идентифицирующие данные человека. С учётом перехода на ID-схему — нужно
   уточнить у юриста объём, но публичная ссылка на политику всё равно
   желательна по умолчанию.
2. **Уведомление в Роскомнадзор** об обработке ПДн — актуальность зависит от
   итога п.1 выше; если данных о личности система не собирает вообще —
   возможно, не требуется, но это должен подтвердить юрист, а не
   предполагаться самостоятельно.
3. **Публичная оферта** — что продаётся (подписка PRO), цена, продление,
   отмена, что при неоплате, **плюс явный пункт про обязанность пользователя
   сохранить свой ID** и последствия его утраты (раздел 5).
4. **Условия возврата** — можно разделом в оферте; прописать момент
   предоставления доступа (важно для цифровых товаров).

Для Chrome Web Store:
5. **Privacy Policy** в Developer Dashboard — отдельно объяснить: само
   расширение ничего никуда не шлёт, кроме своего случайного ID на сервер
   лицензий — никаких данных о личности, журнале или учениках оно не
   передаёт вообще.
6. **Обоснование permissions** для ревью (`background`, фоновая вкладка и т.п.)
   — подготовить текстовое объяснение заранее.

Рекомендовано, не обязательно по закону:
7. **Дисклеймер**: расширение не аффилировано с МЭШ, работает «как есть»,
   расчётные итоги — вспомогательные, финальное решение остаётся за учителем.

Важное решение: **Telegram-бот как канал оплаты не освобождает ни от одного
из этих пунктов** — обязанности привязаны к факту обработки персональных
данных и приёма денег, а не к каналу. Бот можно использовать как UX-слой
поверх тех же документов, но не как способ их избежать.

## 5. Архитектура лицензирования — свой ID вместо кода на email

Финальная схема (после обсуждения): расширение **само генерирует себе
уникальный ID** при установке — никакого email при оплате не требуется в
принципе. Это не код, который кто-то выдаёт — это идентификатор, который
расширение создаёт само и показывает пользователю.

Повторно используем паттерн из проекта «Календарь»: Apps Script Web App как
прокси между расширением и Google Таблицей, ключи никогда не попадают в само
расширение.

```
Расширение при установке само генерирует ID → хранит в chrome.storage.local
        (показывается в панели с явным предупреждением «сохраните его»)

Оплата на эквайринге (Сбербанк, рекуррент) — пользователь вводит на странице
оплаты свой ID (без почты, без других данных)
        ↓ webhook при каждом успешном списании
Google Apps Script Web App
        ↓ помечает ID как PRO/продлевает срок в Таблице
Google Таблица (только база, без ключей внутри)
        ↑ расширение само периодически (раз в сутки) спрашивает:
          «мой ID сейчас PRO?» — и видит обновление автоматически,
          вводить ничего повторно в расширение не нужно
```

Предполагаемые столбцы таблицы:
`ID` | `статус` (свободен/активен/истёк/отозван) | `дата_активации` |
`действует_до` | `устройств_привязано` | `лимит_устройств` (= **1**, жёстко) |
`тариф` | `referral_id` | `referred_by` | счётчик успешных рефералов (для
затухающей награды, см. п.6) | `тип` (оплата/реферал/подарок — см. п.7)

**Лимит устройств — строго 1.** Решено осознанно: это проще и честнее любого
«мягкого» варианта, но означает, что переустановка/смена компьютера требует
восстановления (см. ниже), а не происходит прозрачно.

**Восстановление доступа:** на новой установке — выбор «Новый пользователь»
(сгенерировать новый ID) или «У меня уже есть ID» (ввести сохранённый старый
ID). Если лимит устройств (1) для этого ID уже исчерпан — автоматический
отказ; дальше это уже не автоматизируется, а решается вручную через
обращение в поддержку.

**Email не собирается у пользователей вообще.** Вместо этого — публичный
**email поддержки владельца расширения**, указанный в оферте и в самой
панели расширения (там же, где показан ID, с предупреждением «сохраните ID —
без него восстановить доступ нельзя»), на случай ручных edge-кейсов
(например, ID утерян полностью, лимит исчерпан по уважительной причине).
Такие обращения обрабатываются вручную (владелец сам сверяет оплату и
при необходимости сбрасывает счётчик устройств для конкретного ID в
таблице) — не автоматизируется на старте, редкий случай.

Генерация ID — на лету, самим расширением при установке (не сервером и не
заранее заготовленными пачками).

## 6. Реферальная программа — «Подарок»

- **Приглашённому** — всегда 🎁 **100%** (бесплатный первый месяц), безусловно.
- **Рефереру** — затухающая награда, не плоский лимит:
  - 1-й успешно оплативший приглашённый → 🎁 **100%** (бесплатный месяц);
  - 2-й и далее → 🎁 **50%** скидка на следующий платёж (не целый месяц).
- Награда триггерится только на **первой реальной оплате** приглашённого
  (не на активации триала) — защита от накрутки фейковыми установками.
- Нужен отдельный `referral_id` у каждого PRO-пользователя — постоянный,
  не совпадает с его собственным установочным ID (см. раздел 5), чтобы не
  путать «мой ID для входа» и «мой код для приглашения коллег».
- Нужен счётчик срабатываний на реферера, не просто флаг «награда
  выдана/не выдана» — для затухающей логики 100%→50%.
- Подача в интерфейсе — бейдж «🎁 Подарок», не сухое «скидка N%».
- Затухание (100%→50%) действует **навсегда, без сброса** — счётчик
  накопительный на весь срок жизни аккаунта, не обнуляется ни по году, ни по
  кварталу. Решено, вопрос закрыт.

## 7. Подарочные коды

Третий, отдельный тип кода — независимый от оплаты и от реферальной
программы: владелец (вы) вручную раздаёт PRO-доступ, кому и когда захочет
(маркетинг, благодарность, раздача на презентации и т.п.).

- **Без привязки к email** — код не заранее закреплён за конкретным человеком,
  отдаёте кому угодно (можно даже выложить публично — активирует тот, кто
  первым введёт).
- **Срок — на усмотрение владельца каждый раз**, без стандартного значения по
  умолчанию (1/3/6 месяцев или любой другой — решаете в моменте).
- **Лимита на количество одновременно нет** — полностью на ваше усмотрение,
  система ничего не ограничивает.
- Выдача — двумя способами:
  1. Вручную прямо в Google Таблице (строка: код, статус «свободен»,
     `действует_до` на нужный срок, тип «подарок») — работает сразу, без кода.
  2. Через пункт меню в самой таблице (по аналогии с «Календарь → Добавить
     лист на месяц» в проекте «Календарь»): «Лицензии → Выдать подарочный
     код» — спрашивает срок, сам генерирует код и дату. Удобнее, но требует
     немного кода — делается позже, не обязательно для первого запуска.

## 8. План развития (после запуска, не блокирует публикацию)

- **Второе устройство** — отдельный, более дорогой тариф (второй ID в той же
  оплате), поверх текущего строгого лимита «1 устройство» (см. раздел 2.1).
- **Пуш-уведомления в Telegram** («8Б мало оценок — нужно внимание»):
  - Отправка — простая часть (один запрос к Bot API, токен + chat_id).
  - Привязка Telegram-чата к ID учителя — через тот же Apps Script+Таблицу
    (учитель пишет боту `/start <свой ID>`, бот записывает chat_id в строку).
  - Нужна логика дайджеста (например, раз в день / по итогам «Мой класс»),
    не пуш на каждое событие — иначе спам.
  - Принципиальное ограничение: пуш может слать только само расширение,
    когда оно реально что-то проверило в открытом браузере — сервер
    по-прежнему никогда не видит оценки и не логинится в МЭШ сам. Поэтому
    это не «уведомление в любой момент даже при выключенном компьютере», а
    «уведомление, когда расширение в следующий раз поработало».

## 9. Дашборды

- **Дашборд для владельца — нужен, и он практически бесплатный.** Backend —
  уже Google Таблица (раздел 5), то есть вся база подписок уже там. Делать
  отдельный сайт не нужно:
  1. Отдельный лист с формулами (`СЧЁТЕСЛИ`/`СУММЕСЛИ`): активные подписки,
     кто истекает в ближайшие дни, выручка за месяц, сколько сработавших
     рефералов.
  2. Если нужны графики — Google Looker Studio (бесплатно, подключается
     прямо к Таблице без кода).
  - Делать в числе первых шагов — дёшево и даёт видимость бизнеса сразу.
- **Дашборд для пользователя — решено не делать.** Отдельный сайт
  («посмотреть свою подписку по ID») — лишняя сущность. Статус подписки при
  необходимости можно показывать прямо в панели самого расширения.
