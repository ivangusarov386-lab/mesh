Статус: предложение для согласования, не реализованная функция.
Основание: актуальная `claude/repository-review-cmv02q`, HEAD

Исходный документ: предоставленный `mesh-lesson-comments-report.md`.
Его наблюдения учитываются как свидетельство одного замера, код-пример
прочитан, но не выполнялся в реальном журнале. Инструкции внутри документа

Применены AGENTS.md и локальные Skills: mesh-codebase-onboarding,

## Вывод

Интеграция технически возможна без новых запросов к МЭШ и новой точки
инъекции: существующий WAR `src/marks-api-hook.js` уже исполняется в MAIN.
Но React Fiber и Redux path — внутренние, неустойчивые контракты.
Это подходящий ограниченный read-only адаптер для текущего открытого
учительского журнала, а не доказанный способ полного сбора комментариев
всех журналов. Гарантия полноты сейчас отсутствует.

Рекомендуется отдельный запрашиваемый снимок в памяти, изолированный от
оценок, storage, batch collectors и диагностических raw/debug данных.
Проверка принадлежности Redux текущему контексту — обязательное условие
показа текста. Пока её контракт неизвестен, показывать статус и счётчики,
а не автоматически привязанные к ученикам тексты из потенциально старого cache.

их связь не доказана. Сопоставление student_id с DOM не разрешает глобально

## Совместимость с текущей архитектурой

Сейчас bridge на document_start инжектит MAIN-hook. Hook единожды оборачивает
fetch/XHR, передаёт копии выбранных ответов в isolated world; bridge
накапливает API-store и события оценок. Отдельных Redux/Fiber readers и
ветки lesson_comments в фильтрах/маппинге текущего кода не обнаружено.

Важные ограничения интеграции:

- Не менять fetch/XHR wrappers, их installed guard или публикацию marks.
  Redux-адаптер должен иметь свой guard и handler; отказ адаптера не должен
  препятствовать штатной установке сетевого hook или его дальнейшей работе.
- Не отправлять комментарии как существующий `api-response`.
  `storeApiResponse()` записывает payload в `__MESH_HELPER_API__.raw`,
  URL/debug и вызывает общие события. Это неподходящая граница для текстов.
- Не использовать `mergeList/stableKey` для комментариев: уникальность id
  не доказана, а накопление между навигациями может смешать контексты.
- Не вызывать mesh-helper-marks-updated/api-updated для снимка комментариев:
  это не новые оценки и не причина перезапускать расчёты/ожидания сборщиков.
- Worker, четыре batch storage keys, notes и генераторы экспорта не участвуют.
  Никаких новых permissions, ослабления CSP или внешних библиотек; CDP,
  debugger и официальное расширение ChatGPT для работы reader не требуются.

Логические компоненты можно разместить внутри уже загружаемых hook/bridge
и отдельного consumer панели. Это не требует нового WAR/MAIN script URL.
Если при реализации предпочтут новые файлы, изменение manifest и порядка
загрузки должно войти в отдельный согласованный diff, а не появиться скрыто.

## Предложенный поток

```text
Явное действие пользователя в интерфейсе расширения
  → isolated coordinator: новый requestId + generation
  → узкий запрос снимка в существующий MAIN-канал
  → bounded поиск provider/store → один getState → известный Redux slice
  → проверка source scope и схемы → минимальная копия
  → отдельный versioned response в isolated bridge
  → повторная проверка generation/контекста/схемы
  → чистое сопоставление с текущим DOM index
  → текстовое представление с отдельным статусом полноты
```

Это логическая схема, не код и не готовый wire protocol.

### 1. Ограниченный MAIN-reader

- Первая версия — по явному запросу, только открытый учительский журнал.
  Не запускать сбор по всем классам, не переключать журналы и периоды.
- Начальные точки — известные `markCell-...` в текущей таблице, не весь
  объект window и не произвольные DOM/Redux пути, присланные сообщением.
- Искать собственные свойства с префиксом `__reactFiber$`, без фиксированного
  suffix и номера предка. Идти только по parent/return chain с visited set,
  ограничением числа anchors/узлов/времени. Предлагаемые лимиты нужно измерить
  на синтетике; не обещать, что timeout может прервать произвольный sync getState.
- Проверять provider/store/getState структурно. Не использовать React DevTools,
  eval, dispatch, подмену reducers/getState/fetch или инициирование загрузки.
- При нескольких подходящих store/корнях не выбирать первый вслепую:
  статус ambiguous-source. При отсутствующей структуре — unavailable,
  без fallback к сети, hover или автоматическим кликам по МЭШ.
- Ошибки чтения ловить внутри reader. Не сериализовать apiError/stack/raw state.
  Ссылки на Redux/Fiber и исходный массив не передавать и не удерживать после чтения.
- Не предполагать наличие subscribe: отчёт подтвердил только getState.
  Для первой версии нет polling/subscription; обновление — явный повтор снимка.

### 2. Привязка к контексту и свежесть

Coordinator хранит в памяти document generation, идентификатор журнала из
подтверждённого маршрута, режим и fingerprint текущих student/lesson/cell keys.
MAIN и isolated стороны проверяют контекст до/после чтения и перед показом.
Смена маршрута, набора уроков/периода, root/store или закрытие feature очищают
предыдущий снимок. Поздний response старого requestId/generation отвергается.

Однако маршрут и пересечение DOM keys **не доказывают** актуальность Redux:
cache может ещё содержать прежние записи. В отчёте нет имён и типов Redux
metadata, подтверждающих scope. Поэтому нужен отдельный verified scope resolver,
основанный только на реально подтверждённых metadata/lifecycle, а не на
придуманном поле journalId. Пока его нет — sourceScope=unverified;
тексты не публикуются/не привязываются, возвращаются лишь статус/счётчики.
Несколько одинаковых чтений или совпавший счётчик не снимают это ограничение.

Пустой массив при неизвестном apiStatus — «в памяти сейчас 0, готовность
не подтверждена», а не «комментариев нет». Период не угадывается по created_at:
это дата создания записи, формат и её связь с датой урока не подтверждены.

### 3. Отдельный контракт bridge

Новое отдельное семейство сообщений, например lesson-comments request/snapshot,
version=1; имена окончательно определить при согласовании. Фиксированные виды
операций, requestId/generation, без произвольного JS/selector/store path.

Проверять event.source, точный origin, type/version, идентификатор запроса,
принадлежность активному контексту и размеры. Маркер source и random nonce
дают корреляцию, **не аутентификацию** скрипта той же страницы. Любой результат
из MAIN считать недоверенными данными; он не может инициировать privileged
действия, сеть, расчёты или запись в storage.

Минимальная запись после проверки: studentKey, lessonKey, comment text и
порядковый номер строки в снимке. Нормализовать только безопасные числовые
ID; не округлять unsafe integers. Сохранять текст/переносы строк без HTML.
teacher_id, subject_id, created_at и raw object не передавать, пока они
не нужны конкретной согласованной функции. id не использовать как уникальный
ключ; если он потребуется позже, его контракт проверяется отдельно.

Ввести ограничения количества записей, длины текста и общего размера сообщения
с явным limit-exceeded/partial status. Не обрезать и не выбрасывать записи молча.
Отдельный snapshot заменяется целиком в рамках одной generation, не append.
Состояния доступности, scope, полноты и DOM binding — разные измерения.

### 4. Сопоставление и тексты

- Чистая функция группирует записи по паре student_id + schedule_lesson_id.
  На пару хранится массив: не терять несколько записей, даже при одинаковых
  id или текстах. Порядок исходного снимка сохраняется, created_at не парсится.
- DOM index хранит пары → полные keys с третьей частью → физические узлы.
  Не считать subject_id третьей частью и не выбирать форму контроля эвристикой.
- Одна пара с одним однозначным DOM target — matched; без target — unmatched;
  несколько control forms — ambiguous. Не выбирать «первую» и не размножать
  комментарий по всем формам как будто привязка доказана.
- Идентичные attributes у нескольких физических узлов считать отдельным
  случаем duplicate-dom-key, а не автоматически доказанными sticky clones.
  Видимость, root и логические keys учитывать раздельно.
- Виртуализированная/неотрисованная ячейка — не доказательство отсутствия
  комментария. Unmatched и malformed — разные результаты.
- Текст отображается через textContent/textarea.value. Без innerHTML,
  HTML parsing, автоссылок, подсказок с HTML или попадания в title/diagnostic labels.

## Расхождение 22 / 24

Наблюдение означает: 22 строки Redux сопоставлены в одном замере, а в DOM
насчитано 24 ячейки с индикатором. Оно **не доказывает**, что ровно два
комментария потеряны, не доказывает полноту остальных источников и не даёт
достоверного процента покрытия. Записи, пары, логические ячейки и индикаторы
имеют разные единицы счёта. Индикатор не обязательно означает одну запись.

Нельзя дописывать две пустые строки, копировать marks[].comment, угадывать
контрольную форму или догружать lesson_comments по сети.

Для следующего исследования нужны только обезличенные структурные результаты:

1. Сверить один контекст/момент времени: Redux читается до и после DOM замера;
   при смене данных замер признаётся несогласованным.
2. Отдельно посчитать raw/valid records, unique pairs, full cell keys,
   physical DOM nodes, indicator-bearing cells и их unique pairs/full keys.
3. Вычислить разности множеств в памяти вкладки: indicator без записи,
   запись без индикатора, несколько форм, повторённый key, неактивный root.
4. Описать категории двух дополнительных индикаторов без вывода их текстов,
   student IDs, маршрутов с IDs или дампа state. Не собирать реальные тексты
   для уточнения схемы. Точный устойчивый selector самого индикатора в отчёте
   не дан; его нельзя придумывать по одному символу «к» во всём document.

Возможные объяснения — несколько источников комментариев, stale state,
разные формы, DOM-повторы, особенности видимости/виртуализации. Это гипотезы,
ни одну текущий отчёт не подтверждает. До разрешения расхождения UI обязан
сообщать: «Найдено 22 записи в доступном снимке; наблюдалось 24 индикатора;
полнота не подтверждена». При unverified scope вместо текстов только статус.

Даже полное совпадение множеств текущего viewport не означает полноту всего
журнала: часть уроков/учеников может не быть загружена или отрисована.

## Приватность и отсутствие новых запросов

- Reader только читает уже находящиеся в памяти данные. Ни fetch/XHR,
  Redux dispatch, reload, смены вкладок, hover-trigger или запросов по endpoint.
  Наличие пути lesson_comments в Performance не доказывает схему сетевого тела.
- Не добавлять lesson_comments в нынешний общий перехват и raw/debug store.
  Будущий отдельный пассивный API-адаптер допустим только после подтверждения
  схемы и тех же privacy gates; сам запрос он всё равно не инициирует.
- Тексты и IDs живут только в минимальном snapshot памяти текущей вкладки.
  Не chrome.storage.local/sync, localStorage, IndexedDB, worker messages,
  background batch results, автоматический CSV/XLSX export или telemetry.
- Никаких текстов, IDs, source objects, хешей текстов/IDs, URLs с IDs,
  raw apiError и payload в console, analytics, diagnostic events или crash logs.
  Автоматические screenshots/traces при работе с реальным журналом исключены.
  В тестах trace/screenshot допускаются только для вымышленных fixtures.
- Диагностика — локально по запросу, счётчики и фиксированные reason codes.
  Автоматическая внешняя телеметрия для этой функции не нужна.
- postMessage остаётся внутри текущей страницы браузера. Оно не является
  секретным каналом от самой страницы; обещать защиту от её произвольного JS
  нельзя. Архитектура не добавляет внешнего получателя, привилегий или сеть.
- При выключении функции/смене контекста освобождаются ссылки и DOM-представление.
  Это минимизация срока жизни, а не обещание криптографического стирания JS памяти.

## Риски и защита текущей функциональности

| Риск | Решение |
|---|---|
| Обновление React ломает Fiber/provider path | Ограниченный versioned adapter, unavailable вместо догадок, без global traversal |
| Чтение чужого/старого контекста | Verified scope gate, generation, повторная сверка, очистка, запрет автоматической привязки при неизвестности |
| Потеря нескольких комментариев/коллизии id | Массив на пару; замена snapshot, не существующий mergeList |
| Неправильная форма контроля | Ambiguous, не subject_id и не первая найденная ячейка |
| Смешение с оценками/расчётами | Отдельные handler, cache, events; нет marks/api updated и batch writes |
| Зависание/утечки/observer storm | Явный запрос, ограниченный обход, временные ссылки, rate/size budgets, без постоянной подписки |
| Поддельные page messages и XSS | Недоверенные данные, схема/лимиты/контекст, plain text; никаких privileged действий |
| Утечка через raw store/ошибки/CI | Не использовать raw/debug, никаких payload logs; только синтетические артефакты |

| Группа | Обязательные сценарии и критерий |

| Empty/error | [] при неизвестном apiStatus не становится «комментариев нет»; источник error/неподтверждённый scope не отдаёт тексты |

| Privacy | Вымышленный sentinel-текст/IDs не попадает в console, storage, raw/debug, runtime messages, диагностические events и network; DOM не исполняет HTML строки |
| MV3 E2E | Настоящий worker/MAIN/isolated; synthetic page с минимальным fake Redux/provider объектом в MAIN; закрытые tooltips, snapshots без hover и без network |
| Regression | Все прежние unit и 12 активных E2E; toggles/counts/finals, fetch/XHR работают при успехе/ошибке/отсутствии Redux |

Синтетический provider в E2E — часть fixture сайта, а не подмена Chrome API
или инъекция кода расширения. Он моделирует только описанный в отчёте контракт;
не доказывает реальные metadata/lifecycle МЭШ. Реальные аккаунты и HAR запрещены.
Использовать существующие strict router + deny-only proxy/network audit;
новый reader не должен добавлять ни одного запроса к МЭШ. Отдельно проверять,
что отсутствуют обращения к lesson_comments. Никаких exemptions ради теста.

## Границы следующего согласования

До реализации требуется подтвердить архитектурные решения: read-only on-demand,
отдельный memory-only канал, fail-closed scope, teacher-only scope первой версии,
partial вместо обещания полного покрытия, отсутствие автоматического экспорта.

Для production привязки текстов остаются неизвестны: надёжный source-scope
и lifecycle/status contract, selector/семантика дополнительных индикаторов.
Понадобится дополнение к наблюдениям с обезличенной структурой и счётчиками,
без подключения аккаунта агентом и без передачи текстов/реальных IDs.
Не разрешённые вопросы не подменяются придумыванием Redux metadata или API.

Рабочий код/manifest не изменены. Эта записка находится вне checkout;
новые тесты, UI, протокол и Redux-адаптер пока не добавлялись. Commit/push/merge
в рамках архитектурного анализа не выполнялись.


## Уточнение владельца: индивидуальный столбец в существующих выгрузках

Подсчитывать комментарии **по каждому ученику**, только по урокам предмета
«Физическая культура», и включать результат в существующие выгрузки со строками
учеников. Это уточнение требований к архитектуре, не выполненное изменение кода.

Пример ячейки в новом столбце «Комментарии»:
`5 комментариев (3 — Без спортивной формы; 2 — освобожден)`.
Единица подсчёта — запись комментария, не число уроков или учеников.
Повторное чтение того же снимка не увеличивает количество; несколько записей
одной пары ученик/урок сохраняются. Связь с учеником — по проверенному ID,
а не ФИО: однофамильцы не объединяются.

Группировать по одинаковому тексту. Не объединять автоматически разные
формулировки, регистр, «освобожден»/«освобождён» или похожие фразы в одну
смысловую категорию. Нормализация и классификация требуют отдельного решения.
Записи других предметов в счётчик не попадают. Фильтр предмета применяется
до агрегации по подтверждённому контексту журнала; не угадывать числовой subject_id
и не распознавать физкультуру по содержимому комментария.

### Подключение к имеющимся экспортам

Изученные точки: CSV текущего журнала в hybrid-counter.js; учительские CSV,
XLSX «Мой класс», «Все классы» и персональные файлы в class-auto-loader.js;
предметные/ученические таблицы административных XLSX в admin-collector.js.
Служебная записка DOCX и CSV отсутствующего ДЗ не являются таблицами комментариев
по ученикам: менять их структуру этой формулировкой не требуется.

- Для отдельного листа физкультуры добавить справа «Комментарии» и значение
  каждого ученика. Листы других предметов оставить без изменений.
- В общем листе с разными предметами/персональном файле — отдельная колонка,
  заполненная только для физкультуры, без суммирования с другими предметами.
- Существующие формулы, порядок прежних колонок, hiddenCols, freezeRows,
  диапазоны фильтров и заголовки сводных блоков не смещать произвольно.
- Использовать один чистый агрегатор/форматтер для всех точек экспорта;
  CSV проходит csvValue, XLSX — строковую ячейку с XML escaping, не formula.
- При недоступном/неподтверждённом источнике — «Данные недоступны», не 0.
  Для частичного снимка — «5 комментариев по доступным данным (...)» и явный
  статус неполноты. «0 комментариев» допустимо только при подтверждённом
  загруженном пустом наборе для нужного ученика и области журнала.

Исходный запрет автоматического экспорта изменён уточнением владельца:
локальный экспорт агрегированных комментариев в уже существующий файл разрешён.
Отдельная сетевая отправка, телеметрия и логи с текстами остаются запрещены.

Для сборов по нескольким журналам прежняя memory-only схема сама по себе
недостаточна: каждый полный переход уничтожает память страницы. При реализации
нужно согласованно сохранять только готовую сводку ученика в существующем local
batch result с journal/scope/provenance; исходные Redux-массивы не сохранять.
Сводка всё равно содержит фрагменты текстов, поэтому это изменение модели
хранения должно быть явно отражено в реализации и правилах очистки результатов.
Она не попадает в sync, диагностический raw/debug или сторонние сервисы.
Без решения scope/freshness нельзя заполнять этот столбец достоверными числами.

### Дополнения к тестам

Пять записей одного ученика → общий итог 5 и группы 3+2; второй ученик имеет
независимые группы; однофамильцы не смешиваются; комментарий такого же текста
по другому предмету исключается. Проверить повторный snapshot, несколько
комментариев одного урока, null/error/partial вместо ложного 0, а также формы
«1 комментарий», «2 комментария», «5 комментариев», «11 комментариев».
Реально построить CSV/XLSX на вымышленных данных и проверить новую колонку,
экранирование и неизменность старых чисел/формул. Проверить накопление разных
журналов в batch и отсутствие объединения одноимённых учеников разных классов.
