## Замечания к архитектуре

### 1. Обязательно до показа текстов: подтвердить scope и готовность Redux

В техническом отчёте нет проверенного контракта Redux metadata для текущего
журнала/периода и значений apiStatus. Наличие `apiData`, совпадение DOM ключей
и повтор одинакового снимка не доказывают, что данные не остались от прошлого
контекста. Нельзя выдумывать поле journalId или значение status.

Решение: оставить fail-closed scope gate, отвергать поздние поколения,
до подтверждения контракта не публиковать тексты как актуальные. При unknown,
empty-loading/error запрещён ложный «0 комментариев». Требуется отдельное
уточнение обезличенной структуры/жизненного цикла, без аккаунтов и реальных текстов.

### 2. Обязательно согласовать: хранение при пакетном экспорте

В первоначальной части записки запрещены storage и batch results для текстов,
а экспортное дополнение предлагает local batch summary. Это явно обозначенная
смена модели, но её нужно свести к одному согласованному правилу до реализации.
`class-auto-loader.js:1012` сохраняет результаты каждого журнала перед
полным переходом; память страницы между такими переходами не сохраняется.

Сводка «3 — Без спортивной формы» всё ещё содержит текст комментария,
даже если это не исходный массив. Нельзя называть её анонимным счётчиком.
Варианты для выбора: только выгрузка открытого журнала в памяти либо local
batch summaries с ограниченным сроком жизни и удалением вместе с результатами.
Ни один вариант не должен писать тексты в sync, raw/debug, console или telemetry.
Локальное сохранение не равно сетевой отправке, но требует явных правил очистки.

### 3. Уточнить семантику количества и повторов

Отчёт не подтвердил уникальность record.id и не исследовал несколько записей
одной пары. Сохранять все записи правильно для отсутствия потери данных,
но количество строк массива не обязательно равно числу уникальных комментариев.
Нельзя ни безусловно deduplicate по тексту/id, ни объявлять любой повтор
отдельным достоверным комментарием без проверки source contract.

До проверки — «записи в доступном снимке», замена снимка при повторном чтении,
явный partial status. Пример 3+2 должен тестироваться на пяти вымышленных
самостоятельных записях, а также на повторной выдаче и дублирующемся cache.

### 4. 22 записи / 24 индикатора: полнота не доказана

Индикаторы, DOM-узлы, пары и записи имеют разные единицы измерения.
Два дополнительных индикатора не доказывают потерю ровно двух комментариев.
Нужны разности множеств по snapshot одного контекста и классификация
duplicates/control forms/unmatched, без вывода student IDs или текстов.
Полнота текущего viewport также не равна полноте журнала.

### 5. Экспорт требует проверки колонок и формул

В `class-auto-loader.js:724` лист «Ученик» использует фиксированный диапазон
`$B:$K` и номера VLOOKUP. Слепое добавление колонки в предметный лист не
сделает её доступной на этом сводном листе. В административных таблицах
есть фиксированные индексы summary/highlight и блоков предметов.

Решение: новая колонка справа, явное изменение нужного lookup/диапазона
только для нового значения, все прежние значения/формулы защищены regression.
Для листов других предметов — прежний формат; в смешанной таблице — пустая
ячейка, а не подсчёт комментариев иных предметов. Связь с учеником по ID,
не по ФИО. Нужны реальные synthetic CSV/XLSX с проверкой ZIP/XML/formulas.

## Что архитектура учитывает корректно

- Отдельный MAIN reader, без повторного перехвата fetch/XHR и без сетевых вызовов.
- Отдельный protocol/cache, не существующие storeApiResponse/mergeList.
  Последние действительно сохраняют raw payload и объединяют записи по ключам.
- Пара student_id + schedule_lesson_id; не подмена controlFormId значением subject_id.
- Сохранение нескольких комментариев, explicit ambiguous/unmatched, защита от stale.
- Только физкультура по подтверждённому контексту предмета, не по содержимому текста.
- Plain-text rendering, CSV quoting/formula defense и строковые XML cells.
- Полностью вымышленные fixtures, отсутствие реальных аккаунтов и телеметрии.
